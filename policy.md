# GenAI Use Policy and Prompt Extraction

## GenAI Use Policy

A policy for prompt extraction is established in this protocol, aiming at replicability, transparency, ethics, and bias suppression. However, LLMs are not driven by deterministic models, operating on **non-deterministic** patterns, which means results are not granularly reproducible by third parties. The guarantee of replicability is not linked directly to the output, but rather to the **procedure** applied in its construction.

Regardless, our criterion is to rerun the model across three comparative rounds and identify whether the obtained result is similar in each round through a comparative evaluation, considering the scope, purpose, and objective, using Cohen's Kappa calculated after the rounds, with a minimum value of 0.61 to 0.80 to indicate viability. It is noted that the **human** element will act as a supervisor, observing whether the records in each round are faithful to the input generated by the databases. Furthermore, a criterion of 75% similarity in records will be established as the minimum base to consider the GenAI-assisted round validated. If this value is not reached, manual verification will be conducted without using assisted evaluation tools.

## Prompt Collection

When using LLM models focused on iteration and interaction with the user through chat, the prompts used (inputs) as well as the results (outputs) will be extracted at each conversation or step. They will be stored according to a specific metadata structure in markdown format (`*.md`).

### Metadata Structure

#### Categories

Each prompt must be divided into four categories: 

1. **Extraction:** extraction of raw data from spreadsheets, tabulations, or collections in key-value format, such as `*.xlsx`, `*.xls`, `*.csv`, `*.ris`, `*.bib`, and `*.json`, which can be collected directly from previously selected databases. It is recommended that these data be collected from databases selected according to the developed protocol and not directly requested from the LLM to avoid generating false records. 

2. **Screening:** screening of collected data from spreadsheets, tabulations, or collections in key-value format (`*.xlsx`, `*.xls`, `*.csv`, `*.ris`, `*.bib`, `*.json`). These spreadsheets, tabulations, or collections must have the following fields for each record: * title: string in running text; * authors: array containing the names of the authors in `lastname, firstname` format. Each name is an item in the array; * DOI: digital object identifier of the document; * abstract: abstract in running text as a string, respecting the original length of the document's text; * year: publication year of the document; and * source: tuple of the document's origin, being `journal`, `book`, `chapter`, `section`, `law`, `website`, or others. It is suggested to follow the standard fields of the Zotero management software. 

3. **Synthesis:** generation of a detailed report, in PRISMA 2020 format, with database findings. It is essential to describe every requirement in detail to ensure transparency. In synthesis, generating a text report with the details is fundamental. 

4. **Result:** generation of a spreadsheet or detailed report with the choices made by the LLM model, preferably in markdown. When using this prompt, the original prompt (input) that gave rise to the result must be indicated.

#### Date and Time


Recorded in ISO 8601 timestamp format as a global record, referencing it when generated in an applied protocol. 

#### Platform


Indicate the generation path of the prompt, identifying whether it was via web, CLI (command line interface), or through a direct API to the model. In the case of an API, identify whether it was a developer API of the model or through third parties like OpenRouter or Hugging Face. If the model is installed locally, like Ollama, it will **always be worked with** in CLI format, facilitating screen capture from a pure terminal software/emulator, without the possibility of injection into a graphical interface (like WebUI). 

#### Model 


Record the exact version of the model, indicating its versioned name. In the disclaimer, although not required, it is important to indicate the model in its commercial version. 

#### Temperature 


If a direct API to the model or via third parties is used, the temperature used must be indicated. If not used, "no control" must be declared. 

#### Input 


Documents, spreadsheets, images, videos, and other sources of records that can assist in the context of the systematic review. These elements must be made available as attachments or supplementary material to enable other researchers to achieve levels of similarity in the output. In the case of multi-turn conversations, each described prompt (input) must be reported and each result attached to the prompt. Some models have a "memory" mode; for this reason, it is ideal to either clear this mode or disable it when performing the review. If this is not possible, the memory must be extracted to identify potential biases prior to conducting the systematic review. 

#### Reasoning 


Many LLM models have a simulated "reasoning" process when obtaining information to assist with the output. It is important to document this reasoning when possible, as it can facilitate greater reproducibility and transparency in indicating the paths the model took. 
#### Output 


This element is fundamental to identify what result was achieved. It can be in text format (preferably markdown) or an artifact (in `*.js` or `*.html` formats). The goal is not to generate a ready-made report, but to obtain information regarding the extracted result. In the case of CLI, this result can be a screenshot of the terminal software/emulator. If locally installed models are used, one should always opt for using the CLI and extract the result from the terminal software/emulator. 

#### Human Decision 


Finally, its usability for the research itself is identified in the result, verifying whether the outcome was achieved or not. If the result was not achieved, work is resumed by detailing what was accepted, rejected, and modified for the next round. 

## Rounds and Comparisons 


As a way to partially mitigate the non-deterministic nature of LLM models, it is preferable to perform three rounds with the same prompts. From the generated results, the closeness in the responses of both will be observed objectively with the help of coding software (such as NVivo, Atlas.TI, Iramuteq, among others) or subjectively. Since this is a systematic literature review, the selection of articles for full-text reading will be automated by the LLM model; in this case, the researcher becomes dependent on the model itself. To this end, the extraction of the result indicating the documents selected by the LLM must be compared in each round, as well as the selection criteria. In this case, a minimum threshold of acceptability should be 75%, but a threshold between 75% and 90% similarity is targeted. Cohen's Kappa index should be used to identify selection similarity in screening, with values between 0.61 and 0.80 considered similar. When comparisons occur between LLM models with the purpose of identifying similarities between their choices, Cohen's Kappa or Fleiss's Kappa indices should be used. 

### Unique ID 


Each prompt must have a unique identification, containing category, sequence, date, and model.

```
ID único: PROMPT-[CATEGORIA]-[SEQUÊNCIA]-[DATA]-[MODELO]
      ex: PROMPT-EXTRACTION-001-2026-06-03-CLAUDESONNET4-6
```

## Publicing


It is important that publication is versioned, facilitating chronological control and the internal audit process. In this sense, the Git model (GitHub, GitLab, or others) is fundamental. The recommended structure for creating the repository is:


```
/prompt-registry/
├── README.md           ← explicação metodológica geral
├── protocol.md         ← síntese do uso de IA na pesquisa
├── screening/
│   ├── PROMPT-SCREENING-001-2026-06-03-CLAUDESONNET4-6.md
│   └── ...
├── extraction/
│   ├── PROMPT-EXTRACTION-001-2026-06-03-CLAUDESONNET4-6.md
│   └── ...
├── quality-assessment/ ← protocolo de qualidade
├── synthesis/
└── writing-support/
```

# GenAI Tools to be Used

The following GenAI tools will be used for data analysis:

### Gemini (Google)

* **Model:** gemini-3.5-flash
* **Date of use:** to be confirmed 
* **Format of use:** Gemini WebUI, Antigravity IDE (Google) and Google AI Studio

* **Functions:**
	* Processing files exported from databases (`.ris` and `.bib`): duplicate removal by DOI, title, and authorship; standardization of bibliographic fields; generation of the screening spreadsheet in `.csv` format; 
	* Automated update of the PRISMA 2020 flow at each stage of screening; 
	* Identification of records to be considered for full-text reading by the human supervisor, based on abstracts; 
	* Preliminary application of the quality assessment instrument (adapted CASP), with review and final decision by the principal researcher; and 
	* Generation of the methodological report and final PRISMA 2020 diagram.

### ASReview (Utrecht University)

* **Version:** 3.0.1 
* **Model:** ELAS u4 
* **Date of use:** to be confirmed

* **Function:** Title and abstract screening with active learning, reducing confirmation bias through forced exposure to articles with maximum uncertainty by the algorithm. 
* **Cutoff parameter:** Establishing a threshold as a cutoff line for the model of 200 consecutively rejected records (*not relevant*) to confirm the completion of the review.
